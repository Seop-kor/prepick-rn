# 주문내역 실 데이터 연결

## Problem Statement

주문 목록, 주문 상세, 홈의 진행 중 주문 바는 완성된 UI를 갖추고 있지만 MOCK 데이터를 사용하고 있다. 고객은 실제 자신의 주문과 최신 상태를 볼 수 없으며, 개발자도 실제 API 응답에서 발생하는 페이지네이션, 비동기 로딩, 조회 실패를 검증할 수 없다.

## Solution

GraphQL `orders`와 `order(id)` 쿼리를 기존 API 및 TanStack Query 경계에 연결한다. 주문 목록은 커서 기반으로 조회하고 주문 상세는 개별 주문을 조회하며, 홈은 서버에 추가될 `statuses` 필터로 진행 중 주문만 모든 페이지에서 조회한다. 기존 UI와 상태별 안내 흐름은 유지하되, 실제 스키마의 주문 상태와 생성된 타입을 사용하고 MOCK 데이터는 제거한다.

## User Stories

1. 고객으로서 주문내역 화면에서 내 실제 주문 목록을 보고 싶다. 그래야 매장에서 주문한 내역을 확인할 수 있다.
2. 고객으로서 주문 목록이 날짜별로 묶여 보이기를 원한다. 그래야 원하는 날짜의 주문을 쉽게 찾을 수 있다.
3. 고객으로서 주문이 많을 때 목록 끝에서 이전 주문을 계속 불러오기를 원한다. 그래야 과거 주문까지 확인할 수 있다.
4. 고객으로서 주문이 없을 때 빈 상태와 매장 찾기 동작을 보고 싶다. 그래야 다음 행동을 이어갈 수 있다.
5. 고객으로서 주문 목록 조회에 실패하면 원인을 알고 다시 시도하고 싶다. 그래야 일시적인 네트워크 문제에서 복구할 수 있다.
6. 고객으로서 주문 행을 눌러 실제 주문 상세를 보고 싶다. 그래야 메뉴, 금액, 요청사항, 주문·결제 일시를 확인할 수 있다.
7. 고객으로서 주문 상세가 로딩 중인지 알고 싶다. 그래야 화면이 멈춘 것인지 데이터를 가져오는 것인지 구분할 수 있다.
8. 고객으로서 주문 상세 조회에 실패했을 때 다시 시도하고 싶다. 그래야 뒤로 가지 않고 조회를 재시도할 수 있다.
9. 고객으로서 존재하지 않는 주문과 네트워크 실패를 구분하고 싶다. 그래야 실제로 주문 정보가 없는지 알 수 있다.
10. 고객으로서 서버의 주문 상태를 이해하기 쉬운 한글 문구와 진행 단계로 보고 싶다. 그래야 현재 주문 진행 상황을 알 수 있다.
11. 고객으로서 홈에서 진행 중인 실제 주문과 전체 건수를 보고 싶다. 그래야 주문내역을 직접 찾지 않고도 픽업 상태를 확인할 수 있다.
12. 고객으로서 진행 중 주문이 여러 페이지에 걸쳐 있어도 정확한 건수를 보고 싶다. 그래야 일부 주문을 놓치지 않을 수 있다.
13. 고객으로서 홈의 다른 데이터와 진행 중 주문을 함께 기다리는 동안 기존 스켈레톤을 보고 싶다. 그래야 초기 로딩 화면이 일관되게 느껴진다.
14. 고객으로서 진행 중 주문 조회에 실패해도 홈의 매장과 프로모션은 계속 보고 싶다. 그래야 주문 조회 문제가 다른 홈 기능 이용을 막지 않는다.
15. 개발자로서 주문 API와 상태 판정의 회귀를 자동 테스트로 확인하고 싶다. 그래야 실 데이터 연결 이후 변경에도 기존 동작을 유지할 수 있다.

## Implementation Decisions

### GraphQL과 데이터 모델

- `orders` 쿼리는 목록에 필요한 주문 및 주문 항목 필드와 `nextCursor`를 조회한다.
- `order(id)` 쿼리는 상세에 필요한 동일한 주문 및 주문 항목 필드를 조회한다.
- API의 주문 목록 메서드는 cursor, size, 선택적 statuses를 받아 주문 페이지 전체를 반환하고, 주문 상세 메서드는 id를 받아 주문 또는 null을 반환한다.
- 화면과 상태 유틸리티는 MOCK 전용 타입 대신 GraphQL codegen이 생성한 주문 및 주문 상태 타입을 사용한다.
- 주문 MOCK 데이터, MOCK 지연, MOCK 페이지네이션과 관련 타입을 모두 삭제하고 다른 화면에서도 MOCK을 참조하지 않게 한다.

### 주문 목록과 상세

- 주문 목록은 기존 `useOrders` 무한 쿼리를 유지하고 query function만 실제 API를 사용하도록 교체한다.
- 목록의 페이지 크기는 기존 MOCK과 같은 10으로 유지하고, 서버의 `nextCursor`를 다음 pageParam으로 사용한다.
- 목록의 날짜 그룹, 빈 상태, 초기 스켈레톤, 추가 페이지 로딩, 실패 AlertModal과 재시도 동작은 유지한다.
- 주문 상세는 주문 id를 query key에 포함한 단일 쿼리를 추가해 `order(id)`를 호출한다.
- 상세 초기 로딩에는 ActivityIndicator를 표시한다.
- 상세 조회 실패는 기존 AlertModal 스타일의 오류 메시지와 다시 시도 동작으로 처리하고, API가 null을 반환한 경우에만 기존 ‘주문 정보를 찾을 수 없어요’를 표시한다.
- 상세의 메뉴, 금액, 요청사항, 주문 일시, 결제 일시, 매장 보기 등 기존 UI는 유지한다.

### 홈의 진행 중 주문

- 서버의 nullable `statuses` 인자를 사용해 진행 중 주문만 조회한다. 일반 주문 목록은 statuses를 생략하고, 홈은 CREATED, CONFIRMED, IN_PROGRESS, READY만 전달한다.
- 홈용 주문 조회 함수는 `nextCursor`가 null이 될 때까지 모든 페이지를 순차 조회하고 주문을 하나의 배열로 합친다. 따라서 ‘외 N건’은 첫 페이지가 아닌 실제 진행 중 주문 전체를 기준으로 계산한다.
- 홈용 쿼리는 일반 주문 목록과 구분되는 query key를 사용하고, 진행 중 주문 조회 결과만 홈 주문 바에 전달한다.
- 홈 주문 바는 기존처럼 READY 주문을 우선 보여주고, 여러 건이면 목록으로 이동하며 한 건이면 해당 상세로 이동한다.
- 진행 중 주문 쿼리의 초기 로딩은 기존 홈 로딩 조건에 포함해 다른 홈 데이터와 함께 HomeSkeleton을 표시한다.
- 진행 중 주문 조회 실패는 홈 전체 오류 조건과 공통 재시도 대상에서 제외한다. 홈 본문은 계속 표시하고 주문 바와 그 여백만 제거하며, 주문 실패만으로 홈 AlertModal을 열지 않는다.

### 주문 상태 표현

- CREATED는 ‘주문 확인 중’, ‘주문을 확인하고 있어요’, 진행 단계 0으로 표시한다.
- CONFIRMED는 ‘주문 접수’, ‘주문이 접수됐어요’, 진행 단계 1로 표시한다.
- IN_PROGRESS는 ‘메뉴 준비 중’, ‘메뉴를 만들고 있어요’, 진행 단계 2로 표시한다.
- READY는 목록 라벨만 ‘준비 완료’로 바꾸고 상세 문장은 기존 ‘카운터에서 받아가세요’를 유지하며 진행 단계 3으로 표시한다.
- PICKED_UP은 목록 라벨만 ‘수령 완료’로 바꾸고 상세 문장은 기존 ‘픽업을 완료했어요’를 유지하며 종료 상태로 표시한다.
- CANCELED는 고객 취소와 매장 거절을 모두 포함해 ‘주문 취소’, ‘주문이 취소됐어요’로 표시하고 금액 취소선을 적용한다.
- 별도 REJECTED 상태와 거절 전용 상세 보조 문구는 제거한다.
- CREATED, CONFIRMED, IN_PROGRESS, READY만 진행 중 주문으로 판정하고 PICKED_UP과 CANCELED는 종료 상태로 판정한다.

## Testing Decisions

- 기존 Jest 환경을 유지하고 새 화면 테스트 의존성은 추가하지 않는다.
- 테스트는 내부 호출 횟수보다 API 요청 계약, 반환 데이터, 상태별 외부 표현처럼 모듈 밖에서 관찰 가능한 동작을 검증한다.
- API 테스트는 requestGraphQL을 mock해 주문 목록의 cursor·size·statuses 전달과 페이지 반환, 주문 상세의 id 전달과 주문 또는 null 반환을 검증한다.
- 쿼리 함수 테스트는 진행 중 상태 필터가 전달되는지, 여러 페이지를 끝까지 조회해 순서대로 합치는지, 마지막 페이지 이후 추가 요청이 없는지 검증한다.
- 상태 테스트는 여섯 서버 상태의 목록 라벨, 상세 문구, 진행 단계, 진행 중 여부, 취소 금액 표시 여부를 검증한다. 특히 READY와 PICKED_UP의 목록·상세 문구 차이와 CANCELED의 취소·거절 통합을 확인한다.
- 기존 테스트와 같은 방식으로 src 구조에 대응하는 테스트를 추가한다.
- 목록·상세·홈의 실제 렌더링, 페이지네이션 스크롤, AlertModal 재시도, HomeSkeleton과 주문 바 숨김은 수동으로 확인한다.

## Acceptance Criteria

- [ ] AC-1: 주문 목록은 MOCK이 아닌 `orders` 응답을 날짜별로 표시하고, 주문 행의 매장·메뉴·금액·상태가 실제 응답과 일치한다.
- [ ] AC-2: `nextCursor`가 있으면 목록 끝에서 다음 10개를 조회해 중복 없이 이어 붙이고, null이면 추가 조회하지 않는다.
- [ ] AC-3: 주문이 없으면 기존 빈 상태를 표시하고, 초기·다음 페이지 조회 실패에는 기존 AlertModal과 재시도가 동작한다.
- [ ] AC-4: 주문 상세는 `order(id)` 응답으로 모든 주문 정보를 표시하고 기존 상세 UI를 유지한다.
- [ ] AC-5: 상세 초기 로딩에는 ActivityIndicator가 보이고, 실패와 null 응답을 구분해 각각 재시도 가능한 오류와 정보 없음을 표시한다.
- [ ] AC-6: CREATED, CONFIRMED, IN_PROGRESS, READY, PICKED_UP, CANCELED가 합의한 라벨·문구·진행 단계로 표시된다.
- [ ] AC-7: READY와 PICKED_UP의 목록 라벨은 각각 ‘준비 완료’, ‘수령 완료’이고 상세 문구는 기존 안내 문장을 유지한다.
- [ ] AC-8: CANCELED는 취소와 거절을 모두 ‘주문 취소’로 표시하고 금액 취소선을 적용하며, 별도 REJECTED 처리는 남아 있지 않다.
- [ ] AC-9: 홈은 진행 중 상태만 필터링해 모든 페이지를 조회하고 READY 우선 표시와 정확한 전체 건수를 제공한다.
- [ ] AC-10: 홈 초기 로딩에는 진행 중 주문도 기다리며 HomeSkeleton을 표시한다.
- [ ] AC-11: 진행 중 주문 조회에 실패하면 홈 본문은 유지하고 주문 바만 숨기며, 주문 실패만으로 홈 AlertModal이 나타나지 않는다.
- [ ] AC-12: 주문 관련 화면과 유틸리티는 생성된 GraphQL 타입을 사용하고 MOCK 파일과 모든 MOCK 참조가 제거된다.
- [ ] AC-13: API·전체 페이지 조회·상태 판정 단위 테스트가 통과하고 기존 테스트도 깨지지 않는다.

## Out of Scope

- 서버의 `statuses` 인자 및 필터링 로직 자체 구현
- 주문 목록, 상세, 홈의 시각적 재디자인이나 상세 전용 스켈레톤 추가
- 매장 상세 화면 및 ‘매장 보기’ 이동 구현
- 주문 생성, 취소, 상태 변경 기능
- 주문 상태 실시간 구독이나 주기적 폴링 추가
- React Native Testing Library 등 새 화면 테스트 의존성 도입

## Further Notes

- **구현 전 KAN-4 업데이트 확인 필요:** 서버의 `orders(statuses: ...)` 인자는 아직 스키마가 확정되지 않았다. 담당자가 확정된 서버 스키마를 KAN-4에 업데이트하면, 구현자는 이를 먼저 확인하고 로컬 GraphQL 스키마와 codegen 생성물을 갱신한 뒤 클라이언트를 구현한다.
- `statuses`는 nullable이어야 하며 목록은 인자를 생략하고 홈은 진행 중 상태 배열을 전달한다는 사용 방식만 확정했다. 정확한 목록 타입은 KAN-4의 후속 업데이트를 따르고 임의로 가정하지 않는다.
- codegen 설정은 DateTime을 string으로 생성하므로 기존 날짜 포매팅과 그룹핑 로직을 그대로 사용할 수 있다.
